Production architecture

From 5 tables to 500

The numbers behind "500 independent jobs doesn't work" — and what to build instead.

The binding constraint: Teradata session ceilings

Every TPT job holds open a set of Teradata sessions for its whole lifetime. The limit on how many jobs can run concurrently isn't about Kafka, CPU, or network — it's about how many sessions the target system can host at once.

A number worth being precise about: Teradata's maximum nodes per system configuration is 1,024 — a completely different thing from a session limit, and unrelated to job concurrency. Earlier internal material on this topic conflated the two and quoted "1,024 global sessions" as the ceiling; that was traced back to Appendix B of the Database Administration manual (R20.00) and corrected. The real session ceilings are below.

LimitValue
Max sessions per PE120
Max sessions per gateway vproc1,200 certified maximum, 600 default, tunable

There is no single global session number — total system-wide session capacity is a function of node count × per-gateway limit (one gateway vproc per node by default), not a fixed constant.

What that means for "500 independent jobs"

500 independent TPT jobs at roughly 4 sessions each need about 2,000 sessions. Whether that fits depends on the specific system's gateway/PE topology — but across realistic system sizes, only a fraction of 500 jobs can actually run at once. The rest queue.

Counter-intuitively, larger systems run fewer concurrent independent jobs, not more — a 20-AMP production system runs 38 jobs concurrently while 462 queue, with average queue waits ranging from 10 minutes to 31 hours. That's not real-time ingestion; it's serialized batch wearing a streaming costume. This is the concrete failure mode Scenario A is standing in for at 5-table scale.

Mapping the demo onto 500 tables

A — extrapolates to 500 independent jobs. Not viable on any but the smallest systems; included so the room feels why "one job per table" is the natural first instinct before the numbers above undercut it.

B — extrapolates to the Tier 1 / best-practice production design: 10–30 Debezium connectors grouped by domain, consolidated into 1–3 Kafka topics, 1 TPT job, 1 landing table, one fan-out merge. Independently corroborated at real scale: a logistics customer processing 500M messages/day across 17 sources at 6,200 rows/sec with 0.2% additional CPU; a global automotive manufacturer at 8,000 msg/sec (500M msg/day) via MQ; a telco reference handling 1 billion messages/hour.

C — extrapolates to the tiered pattern: the 10–20 tables that would actually cause business impact if delayed a few seconds (fraud/risk signals, real-time authorization, inventory reservations — identified by asking "which 10–20 would hurt if they lagged 5 seconds?") get dedicated per-table jobs. The remaining ~480 warm/cold tables share one or a handful of consolidated jobs, each on the appropriate TASM tier. Net: roughly 22 concurrent jobs instead of 500, comfortably inside any system's session ceiling, while still giving genuine real-time isolation where it's actually needed.

The one-sentence close

Everything you just watched on the dashboard — job counts, landing latency, the isolation-vs-consolidation tradeoff on kill/restart — is the same mechanism that would run at 500 tables. The only thing that changes between 5 and 500 is which of these three patterns makes sense for your specific tables' latency requirements, not the underlying architecture.
