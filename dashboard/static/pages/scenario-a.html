Scenario A

5 topics, 5 jobs, 5 of everything

The "obvious" approach — and the one that doesn't scale.

The pitch this scenario role-plays: "each table is a Kafka topic, so just give each topic its own ingestion job." It's the instinct almost everyone reaches for first, and at 5 tables it works beautifully — that's the point.

Shape

Kafka topics5 (cdc.public.customer, account, card, payment, transaction)
TPT jobs5 — one per topic, one OS process each
Landing tables5 — DEMO_A.CUSTOMER_LANDING, ACCOUNT_LANDING, CARD_LANDING, PAYMENT_LANDING, TRANSACTION_LANDING
Target tables5 — DEMO_A.CUSTOMER, "ACCOUNT", CARD, PAYMENT, "TRANSACTION"
Merge routines5 — one idempotent MERGE per table, on its own polling loop

How it works

Each job is completely independent end to end: its own Kafka consumer group, its own TPT process, its own landing table, its own merge loop. Nothing is shared between the 5 pipelines except the source topics themselves.

What the tbuild script looks like (transaction table)

tbuild — load_transaction.tbuild (Scenario A)
-- One job: 1 Kafka reader + 1 Stream operator + 1 landing table
DEFINE JOB DEMO_A_LOAD_TRANSACTION
DESCRIPTION 'Scenario A: 1 topic -> 1 TPT job -> 1 target table (transaction)'
(
  DEFINE SCHEMA TXN_RAW_SCHEMA ( PAYLOAD VARCHAR(16000) );

  DEFINE OPERATOR KAFKA_CONSUMER
  TYPE DATACONNECTOR PRODUCER
  SCHEMA TXN_RAW_SCHEMA
  ATTRIBUTES (
    VARCHAR AccessModuleName    = '$(KAFKA_AXSMOD_NAME)',
    VARCHAR AccessModuleInitStr = '-M C -T $(KAFKA_TOPIC) -B $(KAFKA_BOOTSTRAP)
                                    -P * -X group.id=$(KAFKA_GROUP_ID)
                                    -W $(KAFKA_IDLE_TIMEOUT)'
  );

  DEFINE OPERATOR TD_INSERTER
  TYPE STREAM
  SCHEMA TXN_RAW_SCHEMA
  ATTRIBUTES (
    VARCHAR TdpId        = '$(TD_HOST)',
    VARCHAR UserName     = '$(TD_USER)',
    VARCHAR UserPassword = '$(TD_PASSWORD)',
    VARCHAR TargetTable  = '$(TD_DATABASE).TRANSACTION_LANDING'
  );

  STEP MAIN_STEP (
    APPLY ( 'INSERT INTO $(TD_DATABASE).TRANSACTION_LANDING (PAYLOAD) VALUES (:PAYLOAD);' )
    TO OPERATOR (TD_INSERTER)
    SELECT * FROM OPERATOR (KAFKA_CONSUMER);
  );
);

-- Run with: tbuild -f load_transaction.tbuild -j demo_a_transaction -l 5 -z 10
-- Repeat this entire file 4 more times for customer/account/card/payment.
-- 5 files = 5 processes = 5 console windows.

What "job" means concretely

A job is a real tbuild process — e.g. demo_a_transaction — running the Teradata Kafka Access Module against one topic with a 5-second flush interval (-l 5, without which rows would buffer forever and never appear) and 10-second checkpointing (-z 10). On this deployment these run as native Windows processes, each in its own console window, so the room can literally count "5 windows, 5 jobs."

What to expect on the dashboard

The Scenario A card shows a job-count badge like 5/5 jobs running, a per-table row-delta table, and 5 rows in the jobs table — each with its own start / kill / restart buttons. This is the only scenario where those buttons act on 5 independently-addressable things instead of 1 or 2.

The isolation demo moment: click kill on demo_a_transaction. Its row-delta and latency go flat while customer/account/card/payment keep landing rows — and so do Scenarios B and C entirely, since they're unaffected by anything happening in A. Click restart: the job resumes and transaction rows start flowing again. This is genuinely Scenario A's strength: a failure in one table's pipeline cannot touch another table's pipeline.

Why this doesn't scale

That isolation is bought with process count. At 5 tables, 5 processes is completely manageable — a person can watch 5 console windows. At 500 tables, this pattern means 500 independent tbuild processes, each holding its own set of Teradata sessions, each needing its own monitoring, restart logic, and on-call runbook entry.

Worse, it doesn't just get operationally painful — it becomes mechanically infeasible: Teradata's per-PE and per-gateway session ceilings mean only a fraction of 500 independent jobs can run concurrently on any real system size. The rest queue, sometimes for hours. See the scaling page for the exact numbers — this is the load-bearing argument the whole demo is building toward.
