Scenario A

One job per table

Maximum isolation, minimum shared fate — and a cost that grows with every table you add.

What this scenario covers

Scenario A mirrors the source topology exactly: each Kafka topic gets its own TPT job, its own landing table and its own merge routine. Nothing is shared between the five pipelines except the topics themselves.

This is the pattern most teams design first, and for good reason — it is the most defensible one on a whiteboard. Every table is independent, every failure is contained, and every pipeline can be tuned, scheduled and charged separately. At five tables it works cleanly, and this demo runs it for real rather than describing it, so the comparison against B and C is like-for-like.

Shape

Kafka topics5 — cdc.public.customer, account, card, payment, transaction
TPT jobs5 — one per topic, one OS process each
Landing tables5 — DEMO_A.CUSTOMER_LANDING, ACCOUNT_LANDING, CARD_LANDING, PAYMENT_LANDING, TRANSACTION_LANDING
Target tables5 — under DEMO_A
Merge routines5 — one idempotent MERGE per table, each on its own polling loop

The approach

Each job runs a single DATACONNECTOR PRODUCER — the Kafka Access Module subscribed to one topic — feeding a single STREAM operator that inserts the raw Debezium payload into that table's landing table. A per-table merge routine then shreds the JSON envelope into the target table on its own polling loop.

The job definition

tbuild — load_transaction.tbuild (Scenario A, abridged)
-- One job: 1 Kafka reader + 1 Stream operator + 1 landing table
DEFINE JOB DEMO_A_LOAD_TRANSACTION
DESCRIPTION 'Scenario A: 1 topic -> 1 TPT job -> 1 target table (transaction)'
(
  DEFINE SCHEMA TXN_RAW_SCHEMA ( PAYLOAD VARCHAR(16000) );

  DEFINE OPERATOR KAFKA_CONSUMER
  TYPE DATACONNECTOR PRODUCER
  SCHEMA TXN_RAW_SCHEMA
  ATTRIBUTES (
    VARCHAR Format              = 'DELIMITED',
    VARCHAR AccessModuleName    = '$(KAFKA_AXSMOD_NAME)',
    VARCHAR AccessModuleInitStr = '-M C -T cdc.public.transaction -B $(KAFKA_BOOTSTRAP)
                                    -P * -X group.id=$(KAFKA_GROUP_ID)
                                    -W $(KAFKA_IDLE_TIMEOUT)'
  );

  DEFINE OPERATOR TD_INSERTER
  TYPE STREAM
  SCHEMA TXN_RAW_SCHEMA
  ATTRIBUTES (
    VARCHAR TdpId        = '$(TD_HOST)',
    VARCHAR UserName     = '$(TD_USER)',
    VARCHAR UserPassword = '$(TD_PASSWORD)',
    VARCHAR TargetTable  = '$(TD_DATABASE).TRANSACTION_LANDING'
  );

  STEP MAIN_STEP (
    APPLY ( 'INSERT INTO $(TD_DATABASE).TRANSACTION_LANDING (PAYLOAD) VALUES (:PAYLOAD);' )
    TO OPERATOR (TD_INSERTER)
    SELECT * FROM OPERATOR (KAFKA_CONSUMER);
  );
);

-- Run with: tbuild -f load_transaction.tbuild -j demo_a_transaction -l 5 -z 10
-- This entire file is then repeated for customer / account / card / payment.
-- 5 files = 5 processes = 5 things to deploy, monitor and restart.

Note the last comment. The job itself is short and clear — that is the pattern's appeal. The cost is not in any one file; it is in the fact that there are five of them, and at 500 tables there would be 500.

Why it works

Nothing is shared, so nothing can interfere. Each job holds its own Kafka consumer group, its own process, its own Teradata sessions, its own landing table and its own merge. A failure, a slow merge, a schema change or a restart in one pipeline is invisible to the other four. Per-table flush intervals and priorities can be tuned independently, and cost attribution per table is exact.

For a small, stable estate this is a genuinely good design, and it is the right answer more often than the "consolidate everything" reflex admits. The question is only ever how many tables.

Trade-offs

Strengths

  • Complete failure isolation — no shared process, no shared fate
  • Per-table tuning of flush interval, sessions and priority
  • Exact cost attribution and per-table chargeback
  • Simplest mental model — job topology mirrors schema topology
  • Independent restart without coordinating with any other table
  • No fan-out merge logic to design or own

Costs

  • Every artefact multiplies per table — job, landing table, merge, alert, runbook entry
  • Resource footprint scales linearly — 5× the processes and sessions of Scenario B for identical work
  • A schema or connection change means editing one job per table
  • Monitoring noise grows with table count; per-table dashboards stop being readable
  • Deployment and release effort grows with the estate, not the data
  • Operational cost dominates total cost well before data volume does

Failure isolation, live: stopping demo_a_transaction halts only the transaction table. Row deltas and latency for customer, account, card and payment continue unaffected — as do Scenarios B, C and D entirely. Restarting resumes that table alone. This is Scenario A's real and substantial strength.

Where this pattern fits

Choose it when
  • The estate is small and stable — roughly 20 tables or fewer
  • Tables have genuinely different SLAs, priorities or owners
  • Per-table failure isolation is a hard requirement for every table
  • Per-table cost attribution is contractually required
Reconsider when
  • The table count runs to the hundreds
  • Tables share an SLA and an owner — you are paying for isolation nobody uses
  • The estate grows regularly, so every new table means a new deployment
  • The operations team is sized for the data, not for the plumbing

At 500 tables this pattern means 500 job definitions, 500 landing tables, 500 merge routines and 500 entries in the on-call runbook — for the same rows that Scenario B lands with one of each. Scaling to 500 puts numbers on that difference. If some of your tables genuinely need this isolation but most do not, Scenario C is the pattern that gives you both.
