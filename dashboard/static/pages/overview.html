Overview

Loading hundreds of Kafka topics into Teradata

Teradata Parallel Transporter consolidates many streaming sources into one loader. This demo runs four topologies live, side by side, against the same data — so the trade-offs are observed rather than asserted.

The problem this addresses

A modern ingestion estate rarely has one source. It has hundreds: every table in an operational database captured by CDC, every microservice publishing its own event stream, every batch extract landing on a queue. A realistic target is up to 500 Kafka topics feeding 500 Teradata tables, continuously, with business users expecting the warehouse to reflect the source within seconds rather than overnight.

The instinct is to mirror the source topology one-for-one: 500 topics, so 500 loaders. That instinct is reasonable — it maps cleanly onto the schema, isolates every table from every other, and is easy to reason about. It is also the single most expensive decision available, because the loader count, not the data volume, is what you end up operating. Every job is a process to deploy, monitor, alert on, restart, patch and staff. Multiply that by 500 and the pipeline's cost is dominated by its own plumbing.

The core question: does the number of ingestion jobs have to grow with the number of tables? This demo's answer is no — and the four scenarios show exactly what you gain, and what you give up, at each point on that curve.

How TPT loads from Kafka

Teradata Parallel Transporter is a parallel load framework built from operators wired together inside a single job definition. Two kinds matter here:

  • A producer operator reads data in. For Kafka, that's a DATACONNECTOR PRODUCER with the Teradata Kafka Access Module attached — the access module subscribes to a topic and hands rows to TPT as they arrive.
  • A consumer operator writes data out. For continuous low-latency ingestion that's the STREAM operator, which applies row-level DML over multiple Teradata sessions without locking the target table — so the warehouse stays queryable while it loads.

The two are joined by a data stream, declared in SQL-like syntax: SELECT ... FROM OPERATOR (producer) feeds APPLY ... TO OPERATOR (consumer). This is the mechanism the whole demo turns on, because that SELECT is not limited to one producer.

The key property: the Kafka Access Module subscribes one reader to one topic — but a TPT job may declare many producer operators and UNION ALL them into a single data stream feeding one consumer. Adding a topic therefore means adding a few lines to a job definition, not adding a job. That single property is what makes 500 topics tractable.

What is running in this demo

One PostgreSQL database holds 5 tables — customer, account, card, payment, transaction — under continuous, realistic traffic (inserts, updates, deletes). A single Debezium connector captures every change via logical replication and publishes to 5 Kafka topics, one per table.

Scenarios A, B and C then consume those same topics concurrently, through three separate consumer groups, into three parallel Teradata schemas (DEMO_A, DEMO_B, DEMO_C). Nothing is replayed or simulated: all three run live against identical data, so row counts, latency and resource footprint are directly comparable in real time.

Scenario D runs alongside on a different premise. A separate generator publishes flat CSV rows for 3 reference tables (merchant, branch, fx_rate) straight to Kafka — no Postgres, no Debezium. It answers a different question: what changes when the source is already flat rather than a semi-structured CDC envelope.

The four scenarios at a glance

A 5 topics → 5 jobs → 5 landing tables → 5 targets 5 One job per table. Complete failure isolation and the simplest mental model — at a cost that grows linearly with every table added.
B 5 topics → 1 job → 1 landing table → fan-out merge → 5 targets 1 Consolidation. One job serves every topic, and serves 500 the same way it serves 5.
C 5 topics → 2 jobs (1 hot + 1 warm) → 5 targets 2 Tiering. Isolation purchased only for the tables whose SLA actually requires it; consolidation everywhere else.
D 3 flat topics → 1 job → 0 landing tables → 3 targets 1 Direct load. When the source is already flat, TPT upserts straight into the targets — the staging tier disappears.

The patterns compared

Each scenario is a runnable instance of a production pattern. The trade-offs below are what the live dashboard makes visible — every claim here is observable on screen while the pipelines run.

A — Job per table

Strengths

  • Total failure isolation — one table's outage cannot reach another's
  • Per-table tuning, scheduling and priority
  • Trivial to reason about and to attribute cost
  • Per-table restart without touching any other pipeline

Costs

  • Every artefact multiplies: jobs, landing tables, merges, alerts, runbooks
  • Resource footprint scales linearly — 5× the processes and sessions of B for the same 5 tables
  • Schema change means touching one job per table
  • Operational effort dominates total cost long before the data does

B — One consolidated job

Strengths

  • Job count is constant — adding a table adds lines, not processes
  • Smallest possible operational and resource footprint
  • One place to monitor, alert, deploy and restart
  • Landing table doubles as a raw-payload audit and replay trail

Costs

  • Shared fate — stopping the job stops every table it serves
  • One priority for all tables in the job; no per-table SLA
  • Merge cadence, not TPT, tends to dominate end-to-end latency
  • Fan-out merge logic is a component to own and test

C — Tiered

Strengths

  • Real isolation and low latency exactly where the business needs it
  • Consolidated economics for the long tail
  • Per-tier priority and workload management
  • Directly answers a hard isolation or compliance requirement

Costs

  • Two patterns to build, document and operate instead of one
  • Requires an honest, maintained view of which tables are genuinely hot
  • Tier membership drifts as the business changes

D — Direct multi-table load

Strengths

  • No landing tables, no merge routines, no staging storage
  • Lowest latency of the four — TPT flush time alone
  • Fewest moving parts of any pattern here
  • Upsert logic lives in the job, with nothing downstream to schedule

Costs

  • Requires a flat, typed source — not a CDC change envelope
  • No staged raw payload, so no replay-from-landing safety net
  • Shared fate across the tables in the job, as with B
  • Routing logic sits inside the job's DML

Which pattern for which workload

If your workload looks like thisStart here

What the live dashboard shows

The dashboard presents one card per scenario: jobs running, total rows landed, resource footprint (memory, process count and Teradata session count for that scenario's jobs), a per-table breakdown with row deltas and landing latency, and start/kill/restart controls for every job. A single chart tracks end-to-end latency — source commit to Teradata landing — for all four scenarios simultaneously.

The footprint readout is where the isolation-versus-consolidation trade-off becomes concrete rather than rhetorical: Scenario A shows 5 processes and 10 sessions for exactly the table set Scenario B serves with 1 process and 2 sessions. Same data, same targets, same moment in time.

Controls make the trade-off directly observable. Stopping one Scenario A job halts one table while the other four continue. Stopping Scenario B's single job halts all five — the honest price of consolidation. A burst control spikes traffic on both generators at once and marks the moment on the latency chart, so cause and effect are visible without narration. A merge-speed toggle shortens the merge cycle to show landing latency fall live, which demonstrates that for A, B and C the merge interval — not the TPT flush — is usually the dominant term in end-to-end latency. Scenario D has no merge loop to shorten, which is precisely the comparison worth making.

How this maps back to 500

This is a 5-table instantiation of a 500-table question. Every mechanism on screen — consumer groups, producer operators, landing tables, idempotent merges, job counts — is the same mechanism that runs at full scale, just smaller. Nothing changes between 5 tables and 500 except which pattern best fits your tables' latency requirements and your operating model.
