Demo overview

What this demo is

Four topologies, watched side by side — three sharing one live CDC stream, plus a fourth that swaps the source for flat CSV.

The setup

A single PostgreSQL database holds 5 tables — customer, account, card, payment, transaction — with continuous, realistic traffic (inserts, updates, deletes) driven by a load generator. A single Debezium connector captures every change from all 5 tables via logical replication and publishes it to 5 Kafka topics, one per table.

From that point, three independent topologies — Scenario A, B, and C — consume the same Kafka topics through three separate consumer groups and load into three parallel Teradata schemas (DEMO_A, DEMO_B, DEMO_C). Nothing is simulated or replayed: all three run continuously, concurrently, against identical live data, so row counts and latency are directly comparable in real time.

Scenario D runs alongside them, but deliberately isn't part of the same stream. A separate, standalone generator publishes flat CSV rows for 3 new reference tables (merchant, branch, fx_rate) straight to 3 Kafka topics — no Postgres, no Debezium. It exists to answer a different question than A/B/C do: not "how do you consolidate CDC ingest," but "what changes when the source data is already flat instead of semi-structured JSON." See the dedicated Scenario D page for why that distinction matters mechanically.

The four scenarios, at a glance

ScenarioShapeWhat it shows
A 5 topics → 5 independent TPT jobs → 5 landing tables → 5 target tables The "obvious" approach — one job per table. Full isolation, simplest mental model, but doesn't scale: 5 processes here, 500 at real scale.
B 5 topics → 1 consolidated TPT job → 1 landing table → fan-out merge → 5 target tables The recommended production pattern. One job handles every topic — and handles 500 exactly the same way it handles 5.
C 5 topics → 2 tiered TPT jobs (1 hot + 1 warm/cold) → 5 target tables The middle ground: per-table isolation only where it earns its keep, consolidation everywhere else.
D 3 non-CDC topics → 1 consolidated TPT job → 0 landing tables → 3 target tables Same "one job" idea as B, but the source is already flat CSV, not semi-structured JSON — so the landing table and merge step disappear entirely.

See the dedicated Scenario A, Scenario B, Scenario C, and Scenario D pages for how each one actually works and what to expect on screen.

Why three scenarios instead of just building the "right" one

Scenario A is deliberately built and run for real, not just described, because "one job per table" is the instinct almost every audience reaches for first — it maps directly onto the source schema and feels safe. Watching it work at 5 tables makes that instinct feel reasonable before the concurrency math in the scaling page undercuts it at 500. Scenario B is what's actually recommended for production. Scenario C exists for the customer who says "but I need per-table isolation for compliance" — it shows that isolation and consolidation aren't mutually exclusive if you apply isolation only where the latency SLA actually demands it.

A fourth topology, a different premise

Scenario B's landing-table-plus-fan-out-merge pattern exists to solve a specific problem: Debezium's JSON envelope (before/after/source) doesn't map onto flat TPT SCHEMA columns, so it gets landed as raw text and shredded later by a downstream MERGE. Scenario D asks what happens to that pattern when the source data is already flat and typed — and the answer, verified live against a real Teradata target, is that it disappears entirely. One TPT job, three comma-joined APPLY clauses sharing one SELECT, upserting straight into DEMO_D.MERCHANT / BRANCH / FX_RATE — zero landing tables, zero merge routines.

This is the same MultiLoad-derived mechanism TPT has supported for decades (up to 5 target tables from one job), just not previously exercised in this demo. It's not a strictly-better replacement for Scenario B's CDC pattern — Scenario D trades away the landing table's raw-payload audit/replay trail, which matters if a customer's compliance story leans on staged raw-event retention. It's the same "consolidate ingest" thesis Scenario B argues for, one step further, for the subset of real-world sources — batch extracts, pre-normalized message-queue feeds, application event streams with a fixed schema — where the data shape allows skipping the landing tier altogether. See the Scenario D page for the exact TPT grammar and the constraints found only by hitting them.

What you'll see on the live dashboard

The dashboard shows one card per scenario — four now, A through D: how many of its jobs are running, total rows landed, an overhead readout (CPU%, memory, process count, and Teradata session count for that scenario's jobs), a per-table breakdown with row deltas, landing latency, and landing-table backlog, and start/kill/restart controls for every job. Below the cards, a single chart tracks end-to-end latency (source commit → Teradata landing) for all four scenarios at once — that latency line is the single most persuasive number in the room, because it's real data hitting four different pipelines simultaneously.

The overhead readout is where the isolation-vs-consolidation tradeoff stops being an abstract argument: Scenario A's card shows 5 processes and 10 sessions running the same table set that Scenario B's card shows as 1 process and 2 sessions. Backlog (rows landed but not yet merged+purged) is the closest available proxy for consumer lag, since TPT's Kafka Access Module doesn't join Kafka's consumer-group protocol and true lag isn't observable through the standard admin API — except on Scenario D's card, where backlog reads 0 by design: there's no landing table for anything to back up in, and that's the point being made.

Top-level "Start everything" / "Stop everything" buttons launch or kill all 9 TPT jobs (5 in A, 1 in B, 2 in C, 1 in D) plus the merge loop in one click, for resetting the whole room-facing state between runs without walking each scenario's controls individually. A merge speed toggle restarts the merge loop at a faster cadence (1s instead of the default 3s) so you can show landing latency drop live — useful for demonstrating that the merge interval, not the TPT flush, is usually the dominant term in end-to-end latency for A/B/C. Scenario D has no merge loop to speed up — its latency is TPT flush time alone, which is exactly the comparison worth making live.

A burst load button spikes traffic on both the main load generator (weighted toward transaction, feeding A/B/C) and the CSV load generator (weighted toward fx_rate, feeding D) at once, so you can watch all four scenarios respond to the same moment side by side — each trigger is marked with a dashed line directly on the latency chart, so the room can see cause and effect without you having to narrate the timing. Kill/restart buttons on individual jobs demonstrate the isolation-vs-consolidation tradeoff directly: killing a Scenario A job stops only its one table; killing Scenario B's single job stops all 5; killing Scenario D's single job stops all 3 of its tables too, the same shared-fate tradeoff as B, just without a landing table underneath it.

What this maps back to

This is a 5-table, 3-topology instantiation of a real architectural question a customer with up to 500 Kafka topics / 500 source tables would face. Every mechanism on screen — consumer groups, landing tables, idempotent merges, job counts — is the same mechanism that would run at that scale, just smaller. The scaling page walks through exactly how the numbers extrapolate, including the corrected Teradata session-concurrency math behind the "500 independent jobs doesn't work" claim. Scenario D maps back differently — not to the 500-topic CDC question, but to whichever fraction of a customer's 500 tables come from sources that are already flat rather than semi-structured, where the landing tier itself can be designed away.
