Scenario D

Flat source, direct load, no staging tier

One consolidated job as in Scenario B — but because the source is already flat and typed, TPT upserts straight into the target tables. No landing table, no merge routine.

What this scenario covers

Scenario B's landing-table-plus-fan-out-merge exists to solve one specific problem: a Debezium change envelope is semi-structured JSON (before / after / source) and does not map onto flat TPT SCHEMA columns, so it is landed verbatim as text and shredded downstream.

Scenario D asks what remains of that pattern when the source data is already flat and typed. The answer, running live here, is that the staging tier disappears entirely: one TPT job, three comma-joined APPLY clauses sharing one SELECT, upserting directly into DEMO_D.MERCHANT, BRANCH and FX_RATE. Zero landing tables, zero merge routines, zero scheduled downstream work.

A deliberately different premise. Scenario D is not fed by Postgres or Debezium. A standalone generator publishes flat CSV rows for three reference-style feeds (merchant, branch, fx_rate) straight to Kafka. It sits alongside A/B/C rather than competing with them, because it answers a different question: not "how do you consolidate CDC ingest," but "what changes when the source shape is already flat."

Shape

Kafka topics3 — csv.merchant, csv.branch, csv.fx_rate
TPT jobs1 — demo_d_all
Landing tables0
Target tables3 — DEMO_D.MERCHANT, DEMO_D.BRANCH, DEMO_D.FX_RATE
Merge routines0 — the upsert happens inside the job's own APPLY DML

The approach

A single APPLY statement can hold multiple comma-joined APPLY clauses, each with its own TO OPERATOR, all fed by one shared SELECT at the end. This is the same grammar classic MultiLoad has used for decades to populate up to five target tables from one job — TPT exposes it directly, and it is what lets one job write to three different tables here.

Two design notes worth knowing before writing one of these. Consumer operators used in this form declare a deferred SCHEMA * rather than a named schema. And because this restricted APPLY grammar accepts no modifiers between TO OPERATOR (...) and the next clause, per-table routing lives inside the DML itself: a RECORD_TYPE discriminator is injected as a literal in each SELECT, the UPDATE guards its type-conversion with a CASE so a non-matching row's CAST is never evaluated, and the INSERT uses a guarded SELECT ... WHERE form so a non-matching row simply inserts nothing.

The job definition

tbuild — load_all.tbuild (Scenario D, condensed)
DEFINE JOB DEMO_D_LOAD_ALL
DESCRIPTION 'Scenario D: 3 CSV topics -> 1 TPT job -> 3 target tables, no landing tables'
(
  -- MERCHANT_SCHEMA / BRANCH_SCHEMA / FX_RATE_SCHEMA: one per topic, narrow, typed
  -- KAFKA_MERCHANT / KAFKA_BRANCH / KAFKA_FX_RATE: one DATACONNECTOR PRODUCER per topic
  -- STREAM_MERCHANT / STREAM_BRANCH / STREAM_FX_RATE: SCHEMA * (deferred),
  --   TargetTable = the real target table, not a landing table

  STEP MAIN_STEP (
    APPLY (
      'UPDATE $(TD_DATABASE).MERCHANT SET ... WHERE :RECORD_TYPE=''merchant''
         AND merchant_id=CASE WHEN :RECORD_TYPE=''merchant'' THEN CAST(:MERCHANT_ID AS BIGINT) END
         AND CAST(:EVENT_TS AS TIMESTAMP(6)) > source_updated_ts;',
      'INSERT INTO $(TD_DATABASE).MERCHANT (...)
       SELECT CASE WHEN :RECORD_TYPE=''merchant'' THEN CAST(:MERCHANT_ID AS BIGINT) END, ...
       WHERE :RECORD_TYPE=''merchant'';'
    )
    TO OPERATOR (STREAM_MERCHANT)
    ,
    APPLY ( /* same shape, guarded on 'branch' */ ) TO OPERATOR (STREAM_BRANCH)
    ,
    APPLY ( /* same shape, guarded on 'fx_rate' */ ) TO OPERATOR (STREAM_FX_RATE)
    -- One shared SELECT feeds all three APPLY clauses:
    SELECT 'merchant' AS RECORD_TYPE, ... FROM OPERATOR (KAFKA_MERCHANT)
    UNION ALL SELECT 'branch' AS RECORD_TYPE, ... FROM OPERATOR (KAFKA_BRANCH)
    UNION ALL SELECT 'fx_rate' AS RECORD_TYPE, ... FROM OPERATOR (KAFKA_FX_RATE);
  );
);
-- tbuild -f load_all.tbuild -j demo_d_all -l 5 -z 10

The UPDATE's CAST(:EVENT_TS AS TIMESTAMP(6)) > source_updated_ts guard also makes the upsert order-safe: a stale event arriving after a newer one is rejected rather than overwriting current data.

Why it works

The landing table in Scenarios A, B and C is not there for its own sake — it exists because a CDC envelope needs somewhere to sit while its structure is unpicked. Remove that requirement and the tier has no job to do. A flat CSV row already has one column per field and one row per business event, which is exactly what a TPT SCHEMA describes, so the operator can bind those fields straight into target-table DML.

This also removes the largest latency term in the other scenarios. For A, B and C, end-to-end latency is dominated by the merge loop's polling interval, not by TPT. Scenario D has no merge loop, so its latency is the TPT flush interval alone — which is why watching D's line against B's on the latency chart is the comparison worth making.

Trade-offs

Strengths

  • No staging tier at all — no landing tables, no merge routines, no staging storage
  • Lowest latency of the four — TPT flush time, with no merge cycle to wait for
  • Fewest moving parts and fewest components to own
  • Nothing downstream to schedule, monitor or keep running
  • Upsert is order-safe by construction, via the event-timestamp guard
  • One job serves many tables, as in Scenario B

Costs

  • Requires a flat, typed source — not applicable to a CDC change envelope
  • No staged raw payload, so no replay-from-landing safety net
  • Shared fate across the tables in the job, exactly as in Scenario B
  • Routing logic lives inside the job's DML, so schema changes mean editing the job
  • The upsert form writes duplicate-key rejects to the operator's error table by design — expected, per-row, and never job-fatal, but it needs routine housekeeping
  • A single job's target-table count is bounded — very wide estates need several jobs

The audit trade-off, stated plainly: Scenario B's landing table doubles as a raw-payload audit trail and a replay safety net if merge logic ever needs correcting. Scenario D has no equivalent staging tier, so that window does not exist. If a compliance story leans on retaining staged raw events, that is a genuine reason to prefer B — this is a trade, not a strict improvement.

Where this pattern fits

Choose it when
  • Sources emit flat, typed rows — batch extracts, pre-normalised queue feeds, fixed-schema event streams
  • Latency matters and a merge cycle is the term you want to remove
  • Reference and dimension data with a natural key and an event timestamp
  • Minimising the number of components is a first-order goal
Reconsider when
  • The source is a CDC change envelope — use Scenario B
  • Staged raw events are needed for audit, replay or reprocessing
  • Target schemas change frequently, since routing lives in the job's DML
  • Source rows need heavy transformation before they are fit to land

At full scale, a meaningful share of most 500-table estates is genuinely flat rather than CDC-derived — batch extracts, message-queue feeds already normalised upstream, application event streams built around a fixed schema. For that share, Scenario D is the pattern: skip the staging tier and let TPT's multi-table APPLY do the upsert, inside the same single consolidated job Scenario B already argues for.
