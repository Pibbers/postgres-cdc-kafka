Scenario D

When the data's already flat: skip the landing table entirely

Same "one consolidated job" idea as Scenario B — but because this source is CSV, not semi-structured JSON, there's no landing table and no separate merge process at all.

The pitch this scenario proves: Scenario B's landing-table-plus-fan-out-merge pattern exists to solve a specific problem — Debezium's JSON envelope (before/after/source) doesn't map onto flat TPT SCHEMA columns, so it gets landed as raw text and shredded later by a downstream MERGE. When the source is already flat and typed — three new reference-style feeds (merchant, branch, fx_rate), not Postgres/Debezium CDC — that problem doesn't exist, and TPT can APPLY-upsert straight into the real target tables from one job. No landing table, no merge loop, no BTEQ script.

Shape

Kafka topics3 — csv.merchant, csv.branch, csv.fx_rate (a standalone synthetic CSV feed, not Debezium)
TPT jobs1 — demo_d_all
Landing tables0
Target tables3 — DEMO_D.MERCHANT, DEMO_D.BRANCH, DEMO_D.FX_RATE
Merge routines0 — the upsert happens inside the TPT job's own APPLY DML

How it works

What the tbuild script looks like

Verified live against a real Teradata target on 2026-07-14: one APPLY statement can hold multiple comma-joined APPLY clauses, each with its own TO OPERATOR, all fed by one shared SELECT at the end — the same grammar classic MultiLoad has used for decades to populate up to 5 target tables from one job. Two non-obvious constraints found only by hitting them: consumer operators in this form must declare SCHEMA * (deferred, not a named schema), and no modifiers (WHERE, IGNORE DUPLICATE ROWS) are accepted between TO OPERATOR (...) and the next clause — so per-table routing is done inside the DML text itself via a CASE-guarded CAST (so a mismatched-type row's cast is never evaluated) and a guarded SELECT ... WHERE form of INSERT (so a non-matching row just inserts nothing, instead of hitting a NOT NULL violation).

tbuild — load_all.tbuild (Scenario D, condensed)
DEFINE JOB DEMO_D_LOAD_ALL
DESCRIPTION 'Scenario D: 3 CSV topics -> 1 TPT job -> 3 target tables, no landing tables'
(
  -- MERCHANT_SCHEMA / BRANCH_SCHEMA / FX_RATE_SCHEMA: one per topic, narrow, typed
  -- KAFKA_MERCHANT / KAFKA_BRANCH / KAFKA_FX_RATE: one DATACONNECTOR PRODUCER per topic
  -- STREAM_MERCHANT / STREAM_BRANCH / STREAM_FX_RATE: SCHEMA * (deferred), TargetTable = the real table

  STEP MAIN_STEP (
    APPLY (
      'UPDATE $(TD_DATABASE).MERCHANT SET ... WHERE :RECORD_TYPE=''merchant''
         AND merchant_id=CASE WHEN :RECORD_TYPE=''merchant'' THEN CAST(:MERCHANT_ID AS BIGINT) END
         AND CAST(:EVENT_TS AS TIMESTAMP(6)) > source_updated_ts;',
      'INSERT INTO $(TD_DATABASE).MERCHANT (...)
       SELECT CASE WHEN :RECORD_TYPE=''merchant'' THEN CAST(:MERCHANT_ID AS BIGINT) END, ...
       WHERE :RECORD_TYPE=''merchant'';'
    )
    TO OPERATOR (STREAM_MERCHANT)
    ,
    APPLY ( /* same shape, guarded on 'branch' */ ) TO OPERATOR (STREAM_BRANCH)
    ,
    APPLY ( /* same shape, guarded on 'fx_rate' */ ) TO OPERATOR (STREAM_FX_RATE)
    SELECT 'merchant' AS RECORD_TYPE, ... FROM OPERATOR (KAFKA_MERCHANT)
    UNION ALL SELECT 'branch' AS RECORD_TYPE, ... FROM OPERATOR (KAFKA_BRANCH)
    UNION ALL SELECT 'fx_rate' AS RECORD_TYPE, ... FROM OPERATOR (KAFKA_FX_RATE);
  );
);
-- tbuild -f load_all.tbuild -j demo_d_all -l 5 -z 10

What to expect on the dashboard

The Scenario D card shows 1/1 jobs running and three target tables with live row counts — but its backlog column always reads 0, on purpose: there's no landing table for anything to back up in. Watch the latency panel next to Scenario B's during a burst — D's latency reflects only the TPT flush interval, with no added wait for a periodic merge-loop cycle the way B's does.

What this trades away: Scenario B's landing table doubles as a raw-payload audit trail — a replay-from-landing safety net if a merge routine ever needs correcting. Scenario D has no equivalent staging tier, so that audit/replay window doesn't exist here. Worth surfacing explicitly if a customer's compliance story leans on staged raw-event retention — this is a real tradeoff, not a strictly-better replacement for B.

Why this matters beyond 3 reference tables

At 500-table scale, plenty of source systems genuinely produce flat, typed export rows — batch extracts, message-queue feeds already normalized upstream, application event streams designed around a fixed schema — rather than a CDC tool's semi-structured change envelope. For exactly those sources, Scenario D is the pattern: skip the landing-and-shred tier entirely and let TPT's own multi-table APPLY mechanism do the upsert, in the same single consolidated job Scenario B already argues for. It's not a replacement for B's CDC pattern — it's the same "consolidate ingest" thesis, one step further, for the subset of sources where the data shape allows it.
