Scenario B

One job, every topic, fan-out at merge time

The recommended pattern for a large CDC estate — because the job count stops tracking the table count.

What this scenario covers

Scenario B reads exactly the same five topics as Scenario A, at the same moment, from the same Kafka cluster — through one TPT job instead of five. Every topic lands in a single shared landing table, and one fan-out merge routes each row to its target.

The property that matters is not that five became one. It is that adding a sixth topic adds a few lines to a job definition rather than a sixth job. The same shape that serves 5 tables serves 500, with the same single process, the same single landing table and the same single merge.

Shape

Kafka topics5 — the same topics as Scenario A, read through a separate consumer group, tpt.demo_b
TPT jobs1 — demo_b_all
Landing table1 — DEMO_B.CDC_LANDING, shared by all 5 tables
Target tables5 — under DEMO_B, identical DDL to Scenario A
Merge routines1 — a single fan-out merge routing each landed row to its target

The approach

The Kafka Access Module subscribes one reader to one topic, so the job declares five separate DATACONNECTOR PRODUCER operators — one per topic — and combines all five with UNION ALL into a single data stream feeding one shared STREAM operator. All five readers are coordinated as one Kafka consumer group.

This is the same mechanism TPT uses to parallelise reads across the partitions of a single topic, applied instead across five different topics. It is standard TPT grammar, not a workaround.

The job definition

tbuild — load_all.tbuild (Scenario B, abridged)
-- One job: 5 DATACONNECTOR PRODUCER operators UNION ALL'd into 1 STREAM
DEFINE JOB DEMO_B_LOAD_ALL
DESCRIPTION 'Scenario B: 5 topics -> 1 TPT job -> 1 landing table -> fan-out merge'
(
  DEFINE SCHEMA CDC_RAW_SCHEMA ( PAYLOAD VARCHAR(16000) );

  -- One DATACONNECTOR PRODUCER per topic; each attaches its own Kafka
  -- Access Module instance. Adding a topic = adding one of these blocks.
  DEFINE OPERATOR KAFKA_CUSTOMER TYPE DATACONNECTOR PRODUCER SCHEMA CDC_RAW_SCHEMA
  ATTRIBUTES ( VARCHAR AccessModuleInitStr = '-M C -T cdc.public.customer -B $(KAFKA_BOOTSTRAP)
                                         -P * -X group.id=$(KAFKA_GROUP_ID)' );

  DEFINE OPERATOR KAFKA_ACCOUNT  TYPE DATACONNECTOR PRODUCER SCHEMA CDC_RAW_SCHEMA
  ATTRIBUTES ( VARCHAR AccessModuleInitStr = '-M C -T cdc.public.account  ...' );

  -- ... KAFKA_CARD, KAFKA_PAYMENT, KAFKA_TRANSACTION defined identically ...

  DEFINE OPERATOR TD_INSERTER TYPE STREAM SCHEMA CDC_RAW_SCHEMA
  ATTRIBUTES (
    VARCHAR TdpId       = '$(TD_HOST)',
    VARCHAR TargetTable = '$(TD_DATABASE).CDC_LANDING'  -- 1 shared landing table
  );

  STEP MAIN_STEP (
    APPLY ( 'INSERT INTO $(TD_DATABASE).CDC_LANDING (PAYLOAD) VALUES (:PAYLOAD);' )
    TO OPERATOR (TD_INSERTER)
    -- All 5 readers combined into a single row stream:
    SELECT * FROM OPERATOR (KAFKA_CUSTOMER)
    UNION ALL
    SELECT * FROM OPERATOR (KAFKA_ACCOUNT)
    UNION ALL
    SELECT * FROM OPERATOR (KAFKA_CARD)
    UNION ALL
    SELECT * FROM OPERATOR (KAFKA_PAYMENT)
    UNION ALL
    SELECT * FROM OPERATOR (KAFKA_TRANSACTION);
  );
);

-- Run with: tbuild -f load_all.tbuild -j demo_b_all -l 5 -z 10
-- 1 file = 1 process = 1 thing to deploy. At 500 topics: still 1 job.

Where per-table structure is restored

Nothing upstream of the merge knows or cares which table a row belongs to — every row lands in CDC_LANDING as an opaque JSON payload. The merge routine is what re-introduces per-table structure: it reads Teradata's native JSON dot-path notation against the landed payload (payload."after".field) and applies one MERGE per target table, filtered to that table's rows. Functionally this is one execution touching five targets, not five separate jobs.

The Debezium envelope carries its own source.table field, so the routing key arrives with the data — the loader does not need to stamp or partition anything.

Why it works

Consolidation is safe here because the five pipelines were never doing five different things. They read from one cluster, write to one database, share an SLA and share an owner. Scenario A pays for isolation between them; Scenario B observes that nobody was using that isolation and declines to pay.

The landing table earns its place for CDC specifically: a Debezium change envelope is semi-structured and does not map onto flat TPT SCHEMA columns, so landing it verbatim as text and shredding it downstream is both the simplest and the most auditable approach. It also leaves a raw-payload trail that can be replayed if merge logic ever needs correcting — a property Scenario A shares but Scenario D deliberately gives up.

Real-world deployments of this shape run comfortably in the range of 8,000–40,000 rows/sec with 100–500ms loader latency, and the pattern is corroborated at scale: a logistics operator processing 500M messages/day across 17 sources at 6,200 rows/sec for roughly 0.2% additional CPU; a global automotive manufacturer at 8,000 msg/sec; a telco reference handling a billion messages an hour.

Trade-offs

Strengths

  • Job count is constant — it does not grow with table count
  • Smallest footprint of any CDC pattern here — 1 process, 2 sessions for all 5 tables
  • One artefact to deploy, monitor, alert on and restart
  • A new table is a job-definition edit, not a new deployment
  • Landing table provides a raw-payload audit and replay trail
  • Merge logic is written once, not once per table

Costs

  • Shared fate — stopping the job stops every table it serves
  • One priority and one flush interval for all tables in the job
  • No per-table SLA — a hot table cannot be favoured over a cold one
  • Merge cadence, not TPT, usually dominates end-to-end latency
  • The fan-out merge is a real component to design, test and own
  • Per-table cost attribution requires tagging rather than falling out for free

If the shared-fate row above is the blocker — and for some tables it legitimately is — Scenario C shows that it does not have to be all-or-nothing.

The trade-off, live: stopping demo_b_all halts all five tables at once, because they share one process. This is the honest cost of consolidation — per-table failure isolation is exchanged for a dramatically smaller operational footprint. Restarting brings all five back together.

Where this pattern fits

Choose it when
  • Tens to hundreds of CDC tables from one or a few source databases
  • Tables broadly share an SLA, an owner and a priority
  • The estate grows — new tables should not mean new deployments
  • Staged raw payloads are wanted for audit or replay
  • Operational simplicity is the constraint that actually binds
Reconsider when
  • Specific tables carry a real-time SLA the shared cadence cannot meet
  • Regulatory separation demands isolated pipelines for named tables
  • The estate is small enough that per-table jobs cost nothing to run
  • The source is already flat — see Scenario D

At full scale this shape becomes 10–30 Debezium connectors grouped by domain, consolidated into 1–3 Kafka topics, feeding one TPT job, one landing table and one fan-out merge that writes to however many target tables exist. Five or five hundred, the job count does not change. See Scaling to 500 for the full comparison.
