Scenario B

5 topics, 1 job, fan-out at merge time

The recommended production pattern — and what "500 tables" would actually look like mechanically.

The pitch this scenario proves: one consolidated job can read every topic and land every table — and it handles 500 tables exactly the same way it handles 5, because the job count doesn't grow with table count.

Shape

Kafka topics5 (same topics as Scenario A — a separate consumer group, tpt.demo_b)
TPT jobs1 — demo_b_all
Landing table1 — DEMO_B.CDC_LANDING, shared by all 5 tables
Target tables5 — DEMO_B.CUSTOMER, "ACCOUNT", CARD, PAYMENT, "TRANSACTION"
Merge routines1 — a single fan-out merge that routes each landed row to its target table

How it works

The Kafka Access Module doesn't support subscribing one reader instance to multiple topics at once, so the job instead declares 5 separate DATACONNECTOR PRODUCER operators — one per topic — and combines all 5 with UNION ALL feeding a single, shared STREAM operator. All 5 readers are coordinated as one Kafka consumer group. This is the same mechanism TPT normally uses to parallelize reads across partitions of one topic, applied instead across 5 different topics.

What the tbuild script looks like

tbuild — load_all.tbuild (Scenario B)
-- One job: 5 DATACONNECTOR PRODUCER operators UNION ALL'd into 1 STREAM
DEFINE JOB DEMO_B_LOAD_ALL
DESCRIPTION 'Scenario B: 5 topics -> 1 TPT job -> 1 landing table -> fan-out merge'
(
  DEFINE SCHEMA CDC_RAW_SCHEMA ( PAYLOAD VARCHAR(16000) );

  -- One DATACONNECTOR PRODUCER per topic (Kafka Access Module instance each)
  DEFINE OPERATOR KAFKA_CUSTOMER TYPE DATACONNECTOR PRODUCER SCHEMA CDC_RAW_SCHEMA
  ATTRIBUTES ( VARCHAR AccessModuleInitStr = '-M C -T cdc.public.customer -B $(KAFKA_BOOTSTRAP)
                                         -P * -X group.id=$(KAFKA_GROUP_ID)' );

  DEFINE OPERATOR KAFKA_ACCOUNT  TYPE DATACONNECTOR PRODUCER SCHEMA CDC_RAW_SCHEMA
  ATTRIBUTES ( VARCHAR AccessModuleInitStr = '-M C -T cdc.public.account  ...' );

  -- ... KAFKA_CARD, KAFKA_PAYMENT, KAFKA_TRANSACTION defined identically ...

  DEFINE OPERATOR TD_INSERTER TYPE STREAM SCHEMA CDC_RAW_SCHEMA
  ATTRIBUTES (
    VARCHAR TdpId       = '$(TD_HOST)',
    VARCHAR TargetTable = '$(TD_DATABASE).CDC_LANDING'  -- 1 shared landing table
  );

  STEP MAIN_STEP (
    APPLY ( 'INSERT INTO $(TD_DATABASE).CDC_LANDING (PAYLOAD) VALUES (:PAYLOAD);' )
    TO OPERATOR (TD_INSERTER)
    -- All 5 readers combined as a single row stream:
    SELECT * FROM OPERATOR (KAFKA_CUSTOMER)
    UNION ALL
    SELECT * FROM OPERATOR (KAFKA_ACCOUNT)
    UNION ALL
    SELECT * FROM OPERATOR (KAFKA_CARD)
    UNION ALL
    SELECT * FROM OPERATOR (KAFKA_PAYMENT)
    UNION ALL
    SELECT * FROM OPERATOR (KAFKA_TRANSACTION);
  );
);

-- Run with: tbuild -f load_all.tbuild -j demo_b_all -l 5 -z 10
-- 1 file = 1 process = 1 window. At 500 tables: still 1 job.

Where the "5 tables" distinction survives

Nothing upstream of the merge knows or cares which table a row belongs to — every row lands in the same CDC_LANDING table as an opaque JSON payload. The single merge routine is what re-introduces per-table structure: it reads Teradata's native JSON dot-path against the landed payload (payload."after".field) and applies one MERGE per target table, filtered to that table's rows. Functionally this is one execution touching 5 targets, not 5 separate jobs.

What to expect on the dashboard

The Scenario B card shows a job-count badge of 1/1 jobs running and a single row in the jobs table — demo_b_all — with one set of start/kill/restart buttons. The per-table row-delta breakdown still shows all 5 tables individually (the fan-out merge keeps that granularity downstream), even though there's only one job and one landing table feeding it.

The tradeoff demo moment: click kill on demo_b_all — and unlike Scenario A, all 5 tables stop landing rows at once, because they share one process. This is the honest cost of consolidation: you trade per-table failure isolation for a dramatically smaller operational footprint. Restarting brings all 5 back together, too.

Why this is the recommended pattern

This is the Tier 1 / best-practice production design, scaled down to 5 tables for the room to watch. At real scale, the same shape handles 10–30 Debezium connectors grouped by domain, consolidated into 1–3 Kafka topics, feeding 1 TPT job, feeding 1 landing table, feeding one fan-out merge that writes to however many target tables exist — 5 or 500, the job count doesn't change.
