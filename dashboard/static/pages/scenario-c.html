Scenario C

Tiered: isolate what's hot, consolidate the rest

Isolation and consolidation are not opposites. Buy isolation only for the tables whose SLA actually requires it.

What this scenario covers

Scenarios A and B present a choice: isolate everything and pay per table, or consolidate everything and share fate. Scenario C rejects the premise. It gives the one table with a genuine real-time requirement its own dedicated job, and consolidates the other four behind a single shared job.

This is the pattern that answers the most common and most legitimate objection to consolidation — "we need per-table isolation" — without accepting the full cost of Scenario A. In practice the objection is almost never about all 500 tables. It is about a specific handful, and those are the ones worth paying for.

Shape

Kafka topics5 — read through separate consumer groups per tier
TPT jobs2 — 1 dedicated (hot) + 1 consolidated (warm/cold)
Landing tables2 — DEMO_C.TRANSACTION_LANDING (hot) and DEMO_C.WARM_LANDING (shared by 4 tables)
Target tables5 — under DEMO_C, same DDL shape as A and B
Merge routines2 — one dedicated for transaction, one fan-out for the other 4

The approach

The hot tier is structurally Scenario A: one topic, one job, one landing table, one merge — with the flush interval and priority tuned for latency. The warm tier is structurally Scenario B: four topics UNION ALL'd into one job, one shared landing table, one fan-out merge — tuned for efficiency. Scenario C is not a third mechanism; it is the two proven mechanisms applied where each is appropriate.

The job definitions

tbuild — load_transaction.tbuild (hot tier)
-- Hot tier: structurally identical to Scenario A's per-table job
DEFINE JOB DEMO_C_LOAD_TRANSACTION
DESCRIPTION 'Scenario C hot tier: transaction gets its own dedicated job'
(
  DEFINE SCHEMA TXN_RAW_SCHEMA ( PAYLOAD VARCHAR(16000) );
  DEFINE OPERATOR KAFKA_CONSUMER TYPE DATACONNECTOR PRODUCER SCHEMA TXN_RAW_SCHEMA
  ATTRIBUTES ( VARCHAR AccessModuleInitStr = '-M C -T cdc.public.transaction -B $(KAFKA_BOOTSTRAP)
                                         -P * -X group.id=$(KAFKA_GROUP_ID_HOT)' );
  DEFINE OPERATOR TD_INSERTER TYPE STREAM SCHEMA TXN_RAW_SCHEMA
  ATTRIBUTES ( VARCHAR TargetTable = '$(TD_DATABASE).TRANSACTION_LANDING' );
  STEP MAIN_STEP (
    APPLY ( 'INSERT INTO $(TD_DATABASE).TRANSACTION_LANDING (PAYLOAD) VALUES (:PAYLOAD);' )
    TO OPERATOR (TD_INSERTER) SELECT * FROM OPERATOR (KAFKA_CONSUMER);
  );
);
-- tbuild -f load_transaction.tbuild -j demo_c_transaction -l 5 -z 10
tbuild — load_warm.tbuild (warm/cold tier)
-- Warm tier: structurally identical to Scenario B (4 topics UNION ALL'd)
DEFINE JOB DEMO_C_LOAD_WARM
DESCRIPTION 'Scenario C warm tier: 4 topics -> 1 job -> WARM_LANDING -> fan-out merge'
(
  DEFINE SCHEMA CDC_RAW_SCHEMA ( PAYLOAD VARCHAR(16000) );
  -- KAFKA_CUSTOMER, KAFKA_ACCOUNT, KAFKA_CARD, KAFKA_PAYMENT defined as in Scenario B
  DEFINE OPERATOR TD_INSERTER TYPE STREAM SCHEMA CDC_RAW_SCHEMA
  ATTRIBUTES ( VARCHAR TargetTable = '$(TD_DATABASE).WARM_LANDING' );
  STEP MAIN_STEP (
    APPLY ( 'INSERT INTO $(TD_DATABASE).WARM_LANDING (PAYLOAD) VALUES (:PAYLOAD);' )
    TO OPERATOR (TD_INSERTER)
    SELECT * FROM OPERATOR (KAFKA_CUSTOMER)
    UNION ALL SELECT * FROM OPERATOR (KAFKA_ACCOUNT)
    UNION ALL SELECT * FROM OPERATOR (KAFKA_CARD)
    UNION ALL SELECT * FROM OPERATOR (KAFKA_PAYMENT);
  );
);
-- tbuild -f load_warm.tbuild -j demo_c_warm -l 5 -z 10
-- Net: 2 jobs. Add a warm table -> edit this file. Add a hot one -> add a job.

Why it works

Isolation is not free, so it should be bought deliberately rather than by default. Scenario C makes the purchase decision explicit and per-table: the transaction stream — the one with a real latency requirement — gets a dedicated process, its own consumer group, its own merge cadence and its own workload priority. Everything else shares.

The question that drives tier assignment is a business one, not a technical one: which tables would actually cause business impact if they lagged five seconds? In practice the honest answer is a short list — fraud and risk signals, real-time authorisation, inventory reservation — and the rest of the estate turns out to tolerate a shared cadence perfectly well. Tiering encodes that answer directly into the architecture.

Because each tier reuses a pattern already proven in isolation, there is nothing novel to validate. The hot tier behaves exactly as Scenario A does; the warm tier behaves exactly as Scenario B does. Both run in this demo simultaneously against the same data as proof.

Trade-offs

Strengths

  • Genuine isolation and low latency exactly where the business requires it
  • Consolidated economics for the long tail of tables that don't
  • Per-tier priority and workload management
  • Directly satisfies a hard isolation or compliance requirement on named tables
  • Job count grows only with the hot list, not the whole estate
  • Composed from two already-proven patterns — nothing new to validate

Costs

  • Two patterns to build, document and operate instead of one
  • Requires an honest, maintained view of which tables are genuinely hot
  • Tier membership drifts as the business changes — it needs periodic review
  • Shared fate still applies within the warm tier
  • Two merge routines and two landing tables rather than one of each
  • Tier boundaries can become political rather than analytical

Both trade-offs, in one topology: stopping demo_c_transaction halts only transaction — Scenario A's isolation behaviour. Stopping demo_c_warm instead halts customer, account, card and payment together while transaction keeps flowing — Scenario B's shared-fate behaviour. Scenario C contains both patterns, so both are demonstrable without leaving the card.

Where this pattern fits

Choose it when
  • SLAs genuinely differ across the estate — some tables are latency-critical, most are not
  • Compliance or regulation demands isolated pipelines for specific named tables
  • A small number of tables carry disproportionate business value
  • Consolidation is the right default but a blanket policy won't survive review
Reconsider when
  • Every table really does share one SLA — Scenario B is simpler
  • Nobody can say which tables are hot, so tiering has no basis
  • The estate is small enough that Scenario A costs nothing
  • The hot list keeps growing until it is the whole estate — that's Scenario A with extra steps

At full scale this becomes the tiered architecture: the 10–20 tables with a real latency requirement get dedicated jobs, and the remaining several hundred share one or a handful of consolidated jobs, each on the appropriate workload tier. Roughly 20–25 jobs instead of 500, while still delivering genuine real-time isolation where it is actually needed. See Scaling to 500 for the full comparison.
