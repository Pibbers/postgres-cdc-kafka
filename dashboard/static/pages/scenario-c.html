Scenario C

Tiered: isolate the hot table, consolidate the rest

The middle ground — for the customer who says "but I need per-table isolation for compliance."

The pitch this scenario proves: isolation and consolidation aren't mutually exclusive. Give the one table that actually needs low-latency isolation its own job; consolidate everything else. This is the same hot/warm/cold tiering the 500-table recommendation uses — just applied to 5 tables instead of 500.

Shape

Kafka topics5 (separate consumer groups per job)
TPT jobs2 — 1 dedicated (hot) + 1 consolidated (warm/cold)
Landing tables2 — DEMO_C.TRANSACTION_LANDING (hot) and DEMO_C.WARM_LANDING (shared by 4 tables)
Target tables5 — all under DEMO_C, same DDL shape as A and B
Merge routines2 — one dedicated MERGE for transaction, one fan-out MERGE for the other 4

How it works

What the tbuild scripts look like

tbuild — load_transaction.tbuild (hot tier, Scenario C)
-- Hot tier: structurally identical to Scenario A's per-table job
DEFINE JOB DEMO_C_LOAD_TRANSACTION
DESCRIPTION 'Scenario C hot tier: transaction gets its own dedicated job'
(
  DEFINE SCHEMA TXN_RAW_SCHEMA ( PAYLOAD VARCHAR(16000) );
  DEFINE OPERATOR KAFKA_CONSUMER TYPE DATACONNECTOR PRODUCER SCHEMA TXN_RAW_SCHEMA
  ATTRIBUTES ( VARCHAR AccessModuleInitStr = '-M C -T cdc.public.transaction -B $(KAFKA_BOOTSTRAP)
                                         -P * -X group.id=$(KAFKA_GROUP_ID_HOT)' );
  DEFINE OPERATOR TD_INSERTER TYPE STREAM SCHEMA TXN_RAW_SCHEMA
  ATTRIBUTES ( VARCHAR TargetTable = '$(TD_DATABASE).TRANSACTION_LANDING' );
  STEP MAIN_STEP (
    APPLY ( 'INSERT INTO $(TD_DATABASE).TRANSACTION_LANDING (PAYLOAD) VALUES (:PAYLOAD);' )
    TO OPERATOR (TD_INSERTER) SELECT * FROM OPERATOR (KAFKA_CONSUMER);
  );
);
-- tbuild -f load_transaction.tbuild -j demo_c_transaction -l 5 -z 10
tbuild — load_warm.tbuild (warm/cold tier, Scenario C)
-- Warm tier: structurally identical to Scenario B (4 topics UNION ALL'd)
DEFINE JOB DEMO_C_LOAD_WARM
DESCRIPTION 'Scenario C warm tier: 4 topics -> 1 job -> WARM_LANDING -> fan-out merge'
(
  DEFINE SCHEMA CDC_RAW_SCHEMA ( PAYLOAD VARCHAR(16000) );
  -- KAFKA_CUSTOMER, KAFKA_ACCOUNT, KAFKA_CARD, KAFKA_PAYMENT defined as in Scenario B
  DEFINE OPERATOR TD_INSERTER TYPE STREAM SCHEMA CDC_RAW_SCHEMA
  ATTRIBUTES ( VARCHAR TargetTable = '$(TD_DATABASE).WARM_LANDING' );
  STEP MAIN_STEP (
    APPLY ( 'INSERT INTO $(TD_DATABASE).WARM_LANDING (PAYLOAD) VALUES (:PAYLOAD);' )
    TO OPERATOR (TD_INSERTER)
    SELECT * FROM OPERATOR (KAFKA_CUSTOMER)
    UNION ALL SELECT * FROM OPERATOR (KAFKA_ACCOUNT)
    UNION ALL SELECT * FROM OPERATOR (KAFKA_CARD)
    UNION ALL SELECT * FROM OPERATOR (KAFKA_PAYMENT);
  );
);
-- tbuild -f load_warm.tbuild -j demo_c_warm -l 5 -z 10
-- Net result: 2 jobs total. Best of both patterns.

What to expect on the dashboard

The Scenario C card shows 2/2 jobs running, an overhead readout of 2 processes and 4 Teradata sessions — between Scenario A's 5/10 and Scenario B's 1/2 for the same 5 tables — and two rows in the jobs table: demo_c_transaction and demo_c_warm, each independently startable/killable/restartable.

Two isolation demo moments, not one: kill demo_c_transaction and only transaction stops (identical to Scenario A's isolation story). Kill demo_c_warm instead, and customer/account/card/payment all stop together (identical to Scenario B's shared-fate story) while transaction keeps flowing untouched. Scenario C lets you show both tradeoffs from Scenarios A and B within one topology, because it deliberately contains both patterns.

Why this is the answer to "we need isolation for compliance"

Scenario A shows full isolation but doesn't scale. Scenario B scales perfectly but has a single shared failure domain. Scenario C shows that those aren't the only two options — isolation can be applied selectively, to just the tables whose latency SLA actually demands it, while everything else consolidates. At 500 tables, this is the tiered architecture: 10–20 hot tables each get a dedicated job, the remaining ~480 warm/cold tables share one or a handful of consolidated jobs — landing around 22 total jobs instead of 500, comfortably within any system's session capacity.
